# SCosmetics

מערכת Full Stack לניהול מכון קוסמטיקה פרה-רפואית. הפרויקט מחולק לשלוש אפליקציות עצמאיות בהתאם לאפיון הקורס:

- `client` — אתר הלקוחות הציבורי והאזור האישי (Next.js).
- `admin` — ממשק המנהלת והקוסמטיקאיות (Next.js).
- `server` — REST API, לוגיקה עסקית ונתונים (FastAPI).

## מה כבר עובד

- דף בית עברי, רספונסיבי ובכיוון RTL.
- קטלוג טיפולים הנטען מ-FastAPI, עם נתוני fallback כאשר השרת כבוי.
- API ראשוני: `GET /health` ו-`GET /api/v1/treatments`.
- שמירת טיפולים ב-SQLAlchemy וזריעת נתוני הדגמה אוטומטית.
- Redis cache קצר לקטלוג; המערכת ממשיכה לעבוד גם אם Redis אינו זמין.
- רישום לקוחה עם ולידציה ושמירת password hash באמצעות Argon2.
- התחברות מאובטחת עם JWT Access Token וחידוש באמצעות Refresh Token.
- נתיב משתמש מוגן ותשתית הרשאות לפי Customer, Beautician ו-Admin.
- צפייה בזמינות מטפלות במרווחי 15 דקות לפי משך הטיפול ושעות העבודה.
- יצירת תור ללקוחה מחוברת: בדיקת הסמכה, שעות עבודה והתנגשויות, עם Redis Lock ו-Transaction במסד הנתונים.
- מסך לקוחות ב-`/portal`: רישום/כניסה, בחירת תור, רכישת חבילת הדגמה, תורים, חבילות, הזמנות ורשימת המתנה.
- חבילות טיפולים: שריון טיפול בעת קביעת תור; הורדת טיפול אחד מהיתרה רק כשהצוות מסמן שהטיפול הושלם.
- ביטול תור עתידי מציע את החלון ללקוחה הראשונה ברשימת ההמתנה למשך 15 דקות.
- ממשק צוות ב־`admin`: התחברות למנהלת/מטפלת, Dashboard אמיתי, יומן תורים וסימון השלמה או אי־הגעה. ייצוא CSV זמין למנהלת בלבד.
- CMS למנהלת: עריכת טקסטים בדף הבית, טיפולים, חבילות, מכשור וכרטיסי צוות. נתונים אלו מוצגים באתר הציבורי לאחר רענון הדף.
- Header משותף לאתר הציבורי ולאזור הלקוחות: עיצוב זהה, אך קישורי ניווט מותאמים לכל עמוד.
- Docker Compose עבור FastAPI, MySQL ו-Redis.
- בדיקות API בסיסיות עם pytest.

## הפעלה מהירה לפיתוח

פתחו שלושה חלונות Terminal משורש הפרויקט.

### 1. Backend

```powershell
cd server
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8004
```

Alembic מנהל את גרסאות מבנה מסד הנתונים. מריצים `upgrade head` לאחר משיכת
שינויים הכוללים migration חדש ולפני הפעלת השרת.

Swagger יהיה זמין בכתובת `http://127.0.0.1:8004/docs`.

### 2. אתר הלקוחות

```powershell
cd client
npm run dev
```

האתר יהיה זמין בכתובת `http://localhost:3000`, ואזור הלקוחות בכתובת
`http://localhost:3000/portal`. יש להשתמש ב-`localhost` בצד הלקוח בהתאם
להגדרת CORS בשרת. ברירת המחדל של ה-API היא פורט `8004`; אם השרת רץ בפורט
אחר, הגדירו `API_BASE_URL` ו-`NEXT_PUBLIC_API_BASE_URL` לכתובת ה-API המתאימה.

### 3. ממשק הניהול

```powershell
cd admin
npm run dev
```

ממשק הניהול יהיה זמין בכתובת `http://localhost:3001`.

כדי ליצור מנהלת ראשונה במסד הנתונים המקומי, הריצו מתוך `server` לאחר
`alembic upgrade head` (החליפו את פרטי הדוגמה בפרטים שלכם):

```powershell
.\.venv\Scripts\python.exe -m scripts.create_admin --email admin@example.com --first-name Sigal --last-name Levi --phone 050-0000000
```

הסיסמה נקלטת בהקלדה נפרדת ואינה מופיעה בפקודה או נשמרת בהיסטוריית ה־Terminal.
לאחר יצירת החשבון התחברו ב־`http://localhost:3001`. חשבונות המטפלות
שנזרעים אוטומטית בפיתוח מקבלים סיסמה אקראית; הם אינם חשבונות התחברות לדוגמה.

## הפעלה עם MySQL ו-Redis

העתיקו את `.env.example` לקובץ `.env`, החליפו את הסיסמאות, ואז הריצו:

```powershell
docker compose up --build
```

אם התקנת Docker המקומית אינה מזהה את פקודת המשנה `compose`, השתמשו בפקודה המקבילה:

```powershell
docker-compose up --build
```

במצב מקומי ללא הגדרת `DATABASE_URL` השרת משתמש במסד SQLite קטן כדי שהתחלת העבודה תהיה פשוטה. בתוך Docker הוא משתמש ב-MySQL לפי דרישות האפיון. אפשר גם להריץ MySQL מקומי ו-Redis ב-Docker כאשר `server/.env` מצביע לשניהם.

`GET /api/v1/appointments/availability` מציג שעות פנויות למשתמש מחובר.
`POST /api/v1/appointments` יוצר תור ללקוחה מחוברת ומחזיר `201`. הבקשה כוללת
`treatment_id`, `beautician_id` ו-`start_time` עם אזור זמן (לדוגמה
`2026-09-14T09:00:00+03:00`). שעה תפוסה מחזירה `409`. יצירת תור דורשת Redis
פעיל; אם הוא אינו זמין, השרת מחזיר `503` ואינו שומר תור. בדיקות היחידה
משתמשות בנעילה מדומה ואינן דורשות Docker.

## הדגמת שלב 4

1. הפעילו MySQL ו-Redis, הריצו את ה-migration ואת שני השרתים לפי ההוראות למעלה.
2. פתחו `/portal` וצרו חשבון לקוחה. בחרו טיפול, תאריך ושעה פנויה וקבעו תור.
3. בלשונית "חבילות" הוסיפו חבילת הדגמה; בלשונית "האזור האישי" בדקו את ההזמנה ואת היתרה. אין כאן סליקה או חיוב אמיתי.
4. קבעו תור נוסף עם החבילה. היתרה לא יורדת בזמן ההזמנה. השלמה באמצעות `PATCH /api/v1/appointments/{id}/complete` דורשת התחברות ב-Swagger בתור מנהלת או מטפלת משויכת. לאחר ההשלמה היתרה יורדת פעם אחת בלבד; שליחה חוזרת אינה מורידה אותה שוב.
5. לבדיקת רשימת המתנה דרושות שתי לקוחות. אחת קובעת תור, השנייה מצטרפת לרשימת ההמתנה לאותו טיפול ויום. כשהראשונה מבטלת את התור העתידי, השנייה רואה הצעה באזור האישי ויכולה לקבוע אותה למשך 15 דקות. אין עדיין הודעות אימייל/SMS או קידום אוטומטי של הצעה שפג תוקפה.

מסך רכישת החבילות פועל במצב `development` בלבד כדי למנוע הצגת רכישה
ללא סליקה במערכת אמיתית. בעת מעבר לייצור נדרשים ספק תשלום, אישור תשלום
ושמירת אסמכתה לפני הקצאת חבילה.

## הדגמת שלב 5

1. הפעילו MySQL, Redis, API, client ו־admin; הריצו `alembic upgrade head` לפני הפעלת ה־API לאחר עדכון קוד.
2. צרו מנהלת באמצעות הפקודה למעלה והתחברו ל־`localhost:3001`.
3. פתחו „תוכן האתר” ושנו כותרת בדף הבית. רעננו את `localhost:3000` וראו אותה באתר.
4. פתחו „צוות האתר”, ערכו את כרטיס מטפלת1, רעננו את דף הבית ובדקו את השינוי. הכרטיסים התצוגתיים אינם משנים את זמינות התורים.
5. פתחו „רשימת ציוד”, ערכו תמונה או תיאור של מכשיר, רעננו את דף הבית ופתחו את הכרטיס המתאים. שמות קובצי תמונה נשמרים כנתיבים תחת `client/public/images` — אין העלאת קובץ בתוך ה־CMS.
6. ב„מטפלות ותזמונים” בחרו מטפלת אמיתית, הסמכה לטיפול ומשמרת שבועית; בדקו ב־`/portal` איך משתנה הזמינות. שעות הן בשעון הקליניקה; יום שני הוא יום מספר 0. „צוות האתר” שולט רק בכרטיסי התצוגה.
7. ב„לקוחות” חפשו לקוחה ועדכנו את פרטיה. באזור האישי שלה אפשר לערוך את פרטי הקשר עצמאית. ב„יומן ותורים” מנהלת יכולה ליצור תור ללקוחה קיימת: בחרו לקוחה, טיפול, תאריך ושעה פנויה (ואפשר גם חבילה מתאימה). על תור עתידי אפשר ללחוץ „שינוי מועד” כדי לבחור שעה או מטפלת אחרות בלי ליצור תור שני. ביטול תור עתידי מציע את המקום לרשימת ההמתנה.
8. ב„טיפולים וחבילות” שנו טיפול או חבילה; טיפול פעיל מוצג בקטלוג הציבורי. ביומן אפשר לצפות בתורים ולסמן השלמה/אי־הגעה לפי הרשאה. דוחות CSV זמינים בלשונית „דוחות וייצוא”.

תשלומים אמיתיים והודעות חיצוניות נשארים במצב הדגמה מכוון להצגה.
ה־CSV של הזמנות מציג רכישות הדגמה, לא הכנסה אמיתית.
השבתת מטפלת או שינוי משמרות אינם מבטלים תורים שכבר נקבעו; יש לבדוק אותם בנפרד.

## בדיקות

```powershell
cd server
.\.venv\Scripts\python.exe -m pytest
```

בדיקת מקביליות מול MySQL ו-Redis אמיתיים אינה חלק מ-`pytest` הרגיל. הפעילו
את שני השירותים ואת שרת ה-API בפורט `8004`, ודאו שקובץ `server/.env` מצביע
אליהם, ואז הריצו מתוך `server`:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_concurrent_booking
```

הסקריפט יוצר לקוחה זמנית, מאתר שעה שבה שתי מטפלות פנויות לאותו טיפול,
ושולח שתי בקשות הזמנה יחד. התוצאה התקינה היא `201` ו-`409`, עם תור אחד בלבד
ב-MySQL. בסיום הוא מוחק רק את הלקוחה והתור שיצר. הוא מסרב לרוץ מול שרת או
מסד נתונים מרוחקים.

בדיקת קביעת תור ושינוי מועד בידי מנהלת מול MySQL ו־Redis מקומיים:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_admin_booking
```

הבדיקה יוצרת מנהלת ולקוחה זמניות משלה, מאמתת שנשמר תור אחד עם אותו מזהה,
ומנקה בסיום את הרשומות הזמניות. היא אינה משתמשת בסיסמת המנהלת האישית.

```powershell
cd client
npm run lint
npm run build
```

ה־workflow בקובץ `.github/workflows/checks.yml` מריץ בדיקות backend ו־lint/build
לשתי אפליקציות Next.js בכל push ו־pull request. תוצאתו ב־GitHub תופיע לאחר העלאת הקוד.

```powershell
cd admin
npm run lint
npm run build
```
